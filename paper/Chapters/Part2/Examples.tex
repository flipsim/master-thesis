\chapter{Programming with Sessions}\label{ch:programming-with-sessions}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

In this section, we illustrate the design of $\piFD$ through a small collection
of concrete session-typed examples: First, we introduce ephemeral (linear) booleans
along with servers, which implement logical connectives. Then, we revisit
the swap function from the introduction. Lastly, we show how asynchronous
communication can be encoded using continuation channels as a buffer.

\section{Ephemeral Booleans}
We use $\oplus$ and $\with$ to represent (linear) boolean values by defining them
in the standard way:
\begin{align*}
  \bool &\coloneq 1 \oplus 1 \\
  \cobool &\coloneq \bot \with \bot
\end{align*}
where $\bool$ and $\cobool$ introduce the types of channel endpoints for
producers and consumers of boolean values, respectively.

Adopting Milner's syntactical convention \cite{Milner1992:PiCalculus}, we can define the logical
constants by the following processes parametrized by their exposed interface channel $x$:
\begin{align*}
  true(x : \cobool) &\coloneq \link{x}{y} \seq y \slselect{z.\link{z}{\sclose}} \\
  false(x : \cobool) &\coloneq \link{x}{y} \seq y \srselect{z.\link{z}{\sclose}}
\end{align*}

However, since $\piFD$ introduces a separate syntactic category for \emph{messages},
we may also choose the following encoding instead:
\begin{align*}
  true &\coloneq \slselect{z.\link{z}{\sclose}} \\
  false &\coloneq \srselect{z.\link{z}{\sclose}}
\end{align*}
We will use both encodings throughout the examples.
For readability, we will sometimes use a different notation for sequencing in examples.

\begin{definition}[Notation for sequencing]
  \[
    P \seq x \leftarrow M \coloneq P \seq xM
  \]
\end{definition}

To consume boolean messages, we encode branching:
\[
  if \; x \; then \; P \; else \; Q
  \coloneq \link{x}{\schoice{x.\link{x}{\swait{P}}}{x.\link{x}{\swait{Q}}}}
\]
where $x \notin \fv(P)$ and $x \notin \fv(Q)$. If we fulfill the future $x$
of the branching process $if \; x \; then \; P \; else \; Q$ with a boolean value,
we end up with the following reductions:
\begin{align*}
        &\; if \; x \; then \; P \; else \; Q \seq x \leftarrow true \\
       =&\; \link{x}{\schoice{x.\link{x}{\swait{P}}}{x.\link{x}{\swait{Q}}}} \seq x \leftarrow true \\
  \contr&\; \link{true}{\schoice{x.\link{x}{\swait{P}}}{x.\link{x}{\swait{Q}}}} \\
       =&\; \link{\slselect{z.\link{z}{\sclose}}}{\schoice{x.\link{x}{\swait{P}}}{x.\link{x}{\swait{Q}}}} \\
  \contr&\; \parcomp{z}{x}{\link{z}{\sclose}}{\link{x}{\swait{P}}} \\
  \contr&\; \link{\sclose}{\swait{P}} \\
  \contr&\; P
\end{align*}
And similarly, $(if \; x \; then \; P \; else \; Q \seq x \leftarrow false) \red Q$.

\subsection{A Negation Server}
Using the definitions above, we can now implement a simple negation server that
receives a boolean and returns its negation. This communication protocol
is captured by the session types $\bool \otimes \cobool$ and $\cobool \parr \bool$,
where the latter is implemented by the server and the former by the client.
\begin{align*}
  &not(client : \bool \otimes \cobool) \coloneq \\
  &\qquad \link{client}{server} \seq \\
  &\qquad server ? (input, output).\{ \\
  &\qquad \qquad if \; input \; \\
  &\qquad \qquad then \; \{ \link{output}{false} \} \\
  &\qquad \qquad else \; \{ \link{output}{true} \} \\
  &\qquad \}
\end{align*}
The server first creates a new channel with endpoints $client$ and $server$,
adhering to the protocols $\bool \otimes \cobool$ and $\cobool \parr \bool$,
respectively. The former is exposed for other processes to communicate with.
At the endpoint $server$, the server receives the channels $input : \bool$
and $output : \cobool$, and, depending on the value received at $input$,
either forwards $false$ or $true$ along $output$.

A simple client $true\_client$ specifies as interface a channel $server : \bool \parr \cobool$
used to communicate with a corresponding server:
\begin{align*}
  &true\_client(server : \cobool \parr \bool) \coloneq \\
  &\qquad \link{server}{client} \seq \\
  &\qquad client ! [v . true(v) \mid res. \link{res}{\star}]
\end{align*}
The client sends the process $true(v)$ as an output process forwarding
true along $v$. The server's response will be received at $res$ and simply
forwarded to a top-level channel $\star$.

Now, we can spark a computation by forking instances of the client and server,
and linking them by their interfaces via \textsc{cut}, resulting in the following
reduction.
{\allowdisplaybreaks
\begin{align*}
  &       &&\; \parcomp{\;client}{\;server}{not(client)}{true\_client(server)} \\
  &\contr &&\; \ssend{x.true(x)}{res.\link{res}{\star}} \leftrightarrow \\
  &       &&\; ?(input, output). \\
  &       &&\; \quad if \; input \; then \; \{\link{output}{false}\} \; else \; \{\link{output}{true}\} \\
  &\contr &&\; (\nu \; output \; res) ((\nu \; input \; x) \\
  &       &&\; \quad (if \; input \; then \; \{\link{output}{false}\} \; else \; \{\link{output}{true}\} \\
  &       &&\; \quad \mid true(x)) \\
  &       &&\; \quad \mid \link{res}{\star}) \\
  &\contr &&\; (\nu \; input \; x) \\
  &       &&\; \quad (if \; input \; then \; \{\link{\star}{false}\} \; else \; \{\link{\star}{true}\} \mid true(x)) \\
  &\red   &&\; \link{\star}{false}
\end{align*}
}

\section{Revisiting Swap}
In the introduction, we considered the proposition $\tau \coloneq (A \otimes B) \multimap (B \otimes A)$
and its term assignment in $\ND$ and $\LK$, which correspond to functions swapping
the components of a pair. Similarly, in $\piFD$, we can define a $swap$ server that coerces a session
of type $A \otimes B$ into a session of type $B \otimes A$. Since implication is not
built into the type system of $\piFD$, we define linear implication $\multimap$, and its dual, subtraction $\prec$:
\begin{align*}
  A \multimap B &\coloneq A^\bot \parr B \\
  A \prec B     &\coloneq A \otimes B^\bot
\end{align*}

They are defined such that $(A \multimap B)^\bot = A \prec B$ and
$(A \prec B)^\bot = A \multimap B$. Using these types, we could have implemented
the interfaces in the example above as follows:
\begin{align*}
  &not(client : \bool \prec \bool) \\
  &true\_client(server : \bool \multimap \bool)
\end{align*}

Revisiting the derivation in Free Deduction from the introduction (translated to $\LFD$ with $\multimap$ and $\prec$)
\begin{center}
  \begin{prooftree}[separation=0.7em]
    \hypo{\tau, \tau^\bot \vdash }

    \hypo{A \otimes B, A^\bot \parr B^\bot \vdash}

    \hypo{B \otimes A, B^\bot \parr A^\bot \vdash}
    \hypo{B, B^\bot \vdash}
    \hypo{A, A^\bot \vdash}
    \infer3[$\otimes$]{A, B, B^\bot \parr A^\bot \vdash}

    \infer2[$\parr$]{A \otimes B, B^\bot \parr A^\bot \vdash}

    \infer2[$\multimap$]{(A \otimes B) \prec (B \otimes A) \vdash}
  \end{prooftree}
\end{center}
we can now give its term assignment:
\begin{align*}
  &swap(c : (A \otimes B) \prec (B \otimes A)) \coloneq \\
  &\qquad \link{c}{c^\bot} \seq \\
  &\qquad c^\bot ? (pair, output) . \{ \\
  &\qquad \qquad pair \leftrightarrow ?(a, b) . \{ \\
  &\qquad \qquad \qquad \link{output}{\ssend{b^\bot.\link{b}{b^\bot}}{a^\bot.\link{a}{a^\bot}}} \\
  &\qquad \qquad \} \\
  &\qquad \}
\end{align*}

\section{Asynchronous Communication} \label{sec:examples:async-communication}
Up until now, we have only considered examples, where clients perform their
output synchronously, i.e., the output and continuation processes start their execution only
after the server has received the client's message. However, $\piFD$ allows
for asynchronous communication as well. We will illustrate the difference using
a server that computes the conjunction of two boolean values.
\begin{align*}
  &and(client : \bool \prec (\bool \prec \bool)) \coloneq \\
  &\quad \link{client}{server} \seq \\
  &\quad server ? (b_1, client) . \{ \\
  &\quad \quad client \leftrightarrow ? (b_2, output) . \{ \\
  &\quad \quad \quad if \; b_1 \; then \\
  &\quad \quad \quad \; \; \{if \; b_2 \; then \; \{\link{output}{true}\} \; else \; \{\link{output}{false}\}\} \\
  &\quad \quad \quad else \\
  &\quad \quad \quad \; \; \{if \; b_2 \; then \; \{\link{output}{false}\} \; else \; \{\link{output}{false}\}\} \\
  &\quad \quad \} \\
  &\quad \} \\
\end{align*}
Notice that, since $\bool$ is linear, the server has to receive and consume
both values. Short-circuiting behavior would require weakening on booleans.

\subsection{A Synchronous Client}
We will first consider a synchronous client. In the example, $P_1(v_1)$ and $P_2(v_2)$
are processes, which eventually forward a boolean value along $v_1$ and $v_2$, respectively.

\begin{align*}
&sync\_client(server : \bool \multimap (\bool \multimap \bool)) \coloneq \\
&\qquad \link{server}{client} \seq \\
&\qquad client ! [ \\
&\qquad \qquad v_1 . P_1(v_1) \mid \\
&\qquad \qquad server . \link{server}{! [v_2 . P_2(v_2) \mid res . \link{res}{\star}]} \\
&\qquad ]
\end{align*}

Reduction in the processes $P_1$ and $P_2$ is stalled for as long as the server
has not received the client's message. However, if  $P_1$ and $P_2$ involve
large computations, we would like to compute them concurrently, without
having to wait for the server.

\subsection{An Asynchronous Client}
The asynchronous client, on the other hand, uses cuts to perform the
computations $P_1$ and $P_2$ concurrently.
\begin{align*}
&async\_client(server : \bool \multimap (\bool \multimap \bool)) \coloneq \\
&\quad (\nu v_2 x_2) (((\nu v_1 x_1) \\
&\quad\quad \quad (server \leftrightarrow ! [ \tilde{v}_1 . \link{\tilde{v}_1}{v_1} \\
&\quad\quad \quad \phantom{(server \leftrightarrow !} \mid server . server \leftrightarrow ! [ \tilde{v}_2 . \link{\tilde{v}_2}{v_2} \mid res . \link{res}{\star} ]]\\
&\quad\quad \quad \mid P_1(x_1))) \\
&\quad\quad \mid P_2(x_2))
\end{align*}
The client communicates with the server via the process
\[
  server \leftrightarrow ! [ \tilde{v}_1 . \link{\tilde{v}_1}{v_1} \mid server . server \leftrightarrow ! [ \tilde{v}_2 . \link{\tilde{v}_2}{v_2} \mid res . \link{res}{\star} ]]
\]
However, this process does not contain the computations for the inputs itself. Instead,
it only tells the server the locations $v_1$ and $v_2$, to which the results will eventually
be forwarded. The computations are then forked in separate processes
$P_1(x_1)$ and $P_2(x_2)$. As a consequence, the client can start computing both boolean
values in parallel without having to wait for either to be received by the server first.

Here, the futures $v_1$ and $v_2$ serve as a FIFO buffer that can receive inputs
asynchronously. \citet{Deyoung2012:LinCutAsync} show that, given a process assignment
from the asynchronous $\pi$-calculus, cut reduction
in intuitionistic linear logic corresponds to asynchronous buffered session semantics.
For demonstration, we will show their term assignment for the rule of $\otimes$:

\begin{center}
  \begin{prooftree}
    \hypo{P_1 \vdash y : A, \Delta_1}
    \hypo{P_2 \vdash x' : B, \Delta_2}
    \infer2[\textsc{l-$\otimes$-i}]{\parcomp{\tilde{x}}{x'}{\parcomp{\tilde{y}}{y}{x\langle\tilde{y},\tilde{x}\rangle}{P_1}}{P_2} \vdash x : A \otimes B, \Delta_1, \Delta_2}
  \end{prooftree}
\end{center}

\begin{remark}
  Since their work is based on intuitionistic linear logic, we translated
  their term assignment to classical linear logic.
\end{remark}

The \enquote{particle}---as Boudol calls them---$x\langle\tilde{y},\tilde{x}\rangle$ forwards the output and continuation channel
to the receiver and can be encoded as
\[
  x\langle\tilde{y},\tilde{x}\rangle \coloneq \link{x}{\ssend{y.\link{y}{\tilde{y}}}{x.\link{x}{\tilde{x}}}}
\]
in $\piFD$. The encoding sends an output message to the receiver, where
both the output and continuation process are $\eta$-expansions. The resulting process
has the typing
\[
  \tilde{y} : A, \tilde{x} : B, x : A^\bot \parr B^\bot \vdash x\langle\tilde{y},\tilde{x}\rangle
\]
Thus, given processes $\Gamma_1, y : A^\bot \vdash P_1$ and $\Gamma_2, x' : B^\bot \vdash P_2$,
we can derive the same typing for $\otimes$---with formulas being collapsed into the antecedent---by
composing $P_1$, $P_2$, and $x\langle\tilde{y},\tilde{x}\rangle$ with \textsc{cut}s.
